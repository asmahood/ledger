# Release Pipeline — Design

Date: 2026-07-23
Status: approved

Ledger's MVP 1.0 milestone is closed, but none of the release machinery described in
`11-release-planning.md` exists yet. This spec covers everything needed to tag and ship `v1.0.0`.

Scope: signing config, `release.yml`, version bump, backup rules, launcher icon, root README.
Out of scope: category-delete UX (#48), CSV export (#19), instrumented tests in CI.

---

## 1. Signing configuration

`app/build.gradle.kts` gains a release `signingConfig` populated from environment variables. It is
created only when `KEYSTORE_PATH` is present:

```kotlin
signingConfigs {
    System.getenv("KEYSTORE_PATH")?.let { path ->
        create("release") {
            storeFile = file(path)
            storePassword = System.getenv("KEYSTORE_PASSWORD")
            keyAlias = System.getenv("KEY_ALIAS")
            keyPassword = System.getenv("KEY_PASSWORD")
        }
    }
}

buildTypes {
    release {
        signingConfig = signingConfigs.findByName("release")
        isMinifyEnabled = false
        proguardFiles(
            getDefaultProguardFile("proguard-android-optimize.txt"),
            "proguard-rules.pro"
        )
    }
}
```

`findByName` returns null when the config was not created, leaving the build unsigned rather than
failing. This keeps `./gradlew assembleRelease` runnable locally without the key, and lets a signed
build be reproduced locally by exporting the same four variables.

This replaces the `r0adkll/sign-android-release` step named in `11-release-planning.md`. That
third-party action is thinly maintained and confines signing to CI; driving it from Gradle removes
the dependency and makes signed builds reproducible in both places. **`11-release-planning.md` must
be updated to match.**

`isMinifyEnabled` stays `false`. This is deliberate, not an oversight: the app is a personal
sideload with no download-size pressure and no code worth obfuscating, and R8 is a common source of
release-only crashes that debug testing never catches. A comment in the build file records the
decision.

## 2. `release.yml`

Triggered by `on: release: types: [published]`, with `permissions: contents: write`.

| Step | Detail |
|---|---|
| Checkout | `actions/checkout@v4` |
| JDK 17 | `actions/setup-java@v4`, temurin |
| Gradle | `gradle/actions/setup-gradle@v4` — mirrors `ci.yml` |
| Unit tests | `./gradlew testDebugUnitTest` — gate before signing |
| Decode keystore | `KEYSTORE_FILE` secret, base64-decoded to `${{ runner.temp }}/release.jks` |
| Build | `./gradlew assembleRelease` with the four env vars set |
| Verify signature | `apksigner verify` — fail the job if the APK is unsigned |
| Upload | rename to `ledger-<tag>.apk`, `gh release upload` |

The signature verification step is not in the original plan and is load-bearing. Because the Gradle
config degrades to an *unsigned* build when secrets are absent, a missing or misnamed secret would
otherwise publish an APK that silently fails to install. Verification turns that into a build
failure.

The keystore is decoded to `runner.temp`, never the workspace, so it cannot be picked up by a build
step or cached.

## 3. Versioning

`versionName` `"1.0"` → `"1.0.0"`, matching the semver rule the release plan already states.
`versionCode` stays `1`.

## 4. Backup rules

Both XML files get explicit includes rather than the stock template comments.

`backup_rules.xml`:

```xml
<full-backup-content>
    <include domain="database" path="." />
    <include domain="sharedpref" path="." />
</full-backup-content>
```

`data_extraction_rules.xml` mirrors this under both `<cloud-backup>` and `<device-transfer>`.

`allowBackup` stays `true`. With CSV export deferred, cloud backup is currently the only recovery
path for a finance app, so the behaviour should be chosen deliberately rather than inherited from a
template.

**Known limitation:** Room runs in WAL mode, so a backup taken while the app is live may capture a
`.db` file whose `-wal` sidecar is in a different state. Including the whole `database` domain
covers the sidecar files, but the backup is not transactionally consistent. This is acceptable for a
personal app and is a reason to treat CSV export (#19) as the real backup story later — not a reason
to skip explicit rules now.

## 5. Launcher icon

The current icon is the stock Android Studio green robot. The `adaptive-icon` wrapper XML is already
correct — both `ic_launcher.xml` and `ic_launcher_round.xml` declare `<monochrome>` — so only the two
layer vectors are template output.

Per `~/Documents/obsidian-notes/android-development/fundamentals/app-icons.md`, density bitmaps must
be generated by Image Asset Studio, never hand-authored. The workflow is therefore:

1. Delete all existing icon resources: `drawable/ic_launcher_foreground.xml`,
   `drawable/ic_launcher_background.xml`, `mipmap-anydpi/`, and the five `mipmap-*dpi/` folders.
2. Two source vectors are provided as standalone files in `art/`, outside `res/`, so Image Asset
   Studio's generated output cannot collide with its own input.
3. Adam runs Image Asset Studio (`res/` → New → Image Asset), pointing the foreground and background
   layers at those files, and it regenerates `mipmap-anydpi-v26/` plus all density bitmaps.

**Sequencing:** steps 1–3 are atomic. Between the delete and the Image Asset Studio run the manifest
references `@mipmap/ic_launcher`, which will not resolve and the build will not compile. No commit
may land in that intermediate state.

Design constraints, from the same note:

- Both layers 108dp × 108dp.
- All essential content inside the centred 66dp safe-zone circle (x, y ∈ [21, 87]).
- Foreground is a **flat single-colour silhouette with no gradients**, because the same drawable is
  reused as the `<monochrome>` layer and gradients render poorly when the system flattens them to a
  themed tint.
- Colours from the existing theme: background `#006B5F` (primary), foreground `#9EF2E3`
  (primaryContainer).

Note: the repo uses `mipmap-anydpi/` where the note prescribes `mipmap-anydpi-v26/`. At `minSdk 26`
these are equivalent; Image Asset Studio will emit the `-v26` form, which resolves the discrepancy
as a side effect.

**Post-generation check:** the current wrapper XML declares a `<monochrome>` layer, and deleting it
means that guarantee is lost. Image Asset Studio only emits `<monochrome>` if its Monochrome layer
is configured during generation. After the run, confirm the generated `mipmap-anydpi-v26/`
`ic_launcher.xml` and `ic_launcher_round.xml` still contain `<monochrome>`; if not, add it back by
hand pointing at `@drawable/ic_launcher_foreground`. Without it, themed icons on Android 13+ silently
regress to a washed-out auto-generated stand-in.

## 7. Verification

- Unit tests run in CI on every PR.
- Instrumented suite (108 tests) run on the physical Pixel 9 Pro before tagging — never an emulator.
- The signed APK installs on-device.
- A backup/restore round-trip is confirmed to actually restore transactions before the backup
  behaviour is trusted.

## 8. Manual steps (Adam)

These involve key material or GUI tooling and are not automated:

1. Generate the release keystore with `keytool`, run directly so no password passes through an
   agent tool call or shell history.
2. Store the passwords in a password manager and back up the `.jks` — it cannot be regenerated, and
   losing it means never being able to ship an upgrade to an installed APK.
3. Set four repository secrets: `KEYSTORE_FILE` (base64), `KEYSTORE_PASSWORD`, `KEY_ALIAS`,
   `KEY_PASSWORD`.
4. Run Image Asset Studio to generate the icon resources.

`.gitignore` already covers `*.jks` and `*.keystore`.
